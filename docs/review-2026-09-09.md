# Full project review — 2026-09-09

Scope: everything in `experiment/` (both tasks, `run_battery.m`, all 46 files
in `+utils`), the stimulus CSVs, and the docs. Goal: ready for data collection
next week — polished, collecting the *correct* data, clear to participants,
and flexible about what each participant sees.

Overall: the architecture is genuinely good. Participant manifests,
deterministic seeding, crash recovery, elicitation caching, the PLAN
dispatcher, AOI thresholds in degrees, BDM incentive-compatibility — all of
that is sound and better documented than most lab code. The problems below
are mostly small and fixable in a day or two, but three of them are blockers
and several would quietly corrupt or lose data.

---

## A. Blockers

### A1. The jobs stimulus pipeline is missing from the repo
`utils/config.m:93` points the jobs domain at
`prepared/job_stimuli_<arm>.csv` produced by `stimgen/prepare_stimuli.py` —
but there is no `stimgen/` directory, no `prepared/` output, and no configs
anywhere in this repo. Only the pipeline's README survived (twice:
`experiment/README-original.md` and the untracked `docs/housing_wages_readme.md`
are both copies of it). The checked-in `experiment/stimuli/job_stimuli.csv`
is **not** a substitute: it lacks the generated columns
(`commuteMinutes`, `ptoDays`, `hoursPerWeek`, `workArrangement`) that
`utils/attributes.m` declares, so even pointing config at it would crash the
first time one of those attributes is selected for display.

**Action:** recover `prepare_stimuli.py`, the `configs/*.json`, and the
`prepared/` outputs + provenance JSONs from the OSU share
(`\\asc-files.asc.ohio-state.edu\projects\PSY-kvam.4\housing_wages\Experiment\stimuli\`),
commit them, and restore the `stimgen/` layout the READMEs describe. Until
this is done the jobs domain cannot run from this repository at all.

### A2. Auction crashes when a participant completes some episodes with a bid and some without
`auction_task.m`: `trial.bidRT` is only assigned inside the bid path
(line 489). Episodes that end by timeout or exhaustion never get the field.
The accumulation `trials(end+1) = trial` (line 229) then throws
*"Subscripted assignment between dissimilar structures"* the first time bid
and no-bid episodes are mixed — i.e. it survives quick dev tests (where you
always bid) and dies mid-session with a real participant.

**Fix:** add `trial.bidRT = NaN;` to the defaults block at lines 342–348.

### A3. Payout computation crashes if incentives are ever enabled
`utils/incentives.m:129–130` formats `pick.block`, but `utils.collectWins`
entries have no `block` field (they have `trial`). Enabling
`cfg.incentives.enabled` with ≥1 win → "Reference to non-existent field".
Dormant today, but the README explicitly contemplates turning incentives on.

## B. Data-correctness issues

### B1. Timed-out choice trials are scored as preference reversals
`continuous_DC_task.m` `scoreReversals`: a timed-out choice leaves
`choseMoney = NaN`, and `NaN ~= pricedMoneyHigher` evaluates **true**, so
every timed-out choice with priced pair-mates is recorded as a reversal —
biasing the headline DV upward. Skip trials with `timedOut` or NaN
`choseMoney`.

### B2. No AOI geometry is saved (or validated) for the contdc task
`drawCard` computes and returns per-attribute AOI rects; both callers
discard the return value. `dataMat.(domain)` for contdc stores no
`aoiRects`/`aoiNames`, and `utils.checkAOIs` never runs on the card layouts
(it only runs on the auction's 6-tile grid). Gaze data from the entire
contdc task cannot be mapped to attributes from the data file alone — it
would have to be reconstructed from the layout code, which is exactly the
failure mode `checkAOIs` was written to prevent.

### B3. Same gap for the auction's detail view
The detail panel (`showDetail`) is where the actual inspection gaze happens,
and its per-attribute panel rects are computed inline, never validated by
`checkAOIs`, and never saved. Only the search-grid AOIs are.

### B4. No clock-sync anchor between gaze and events
The event log is keyed to PTB `GetSecs`/flip times; Tobii samples carry
Tobii system timestamps. Nothing records a correspondence pair, so aligning
gaze to `option_appear`/`detail_enter` events rests on the assumption that
both clocks are identical. Record `Tobii.get_system_time_stamp()` alongside
`GetSecs` at run start and end (two pairs gives you offset *and* drift), and
store it in the gaze file.

### B5. Latent index-misalignment in `utils/sampleWindow.m`
Line 22 removes NaNs from `values`; line 41 computes `w.idx` as indices
into the *filtered* vector; both tasks then do `stimuli(win.idx, :)` on the
*unfiltered* table. Both current CSVs happen to have zero missing values, so
this is silent today — but any future prepared jobs file with one missing
wage shifts every index and the participant silently sees (and the data
records) the wrong stimuli. Compute the mask on the original vector instead.

### B6. contdc runs on the global RNG stream; auction doesn't
`continuous_DC_task.m:42` uses `RandStream.getGlobalStream` (seeded as a
side effect of `beginRun`'s `rng(run.seed)`), while `auction_task.m:37`
builds a private stream from `run.seed`. The contdc stream is therefore
deterministic only until anything else consumes global RNG —
`utils.elicitVAS` line 32 already does (`randperm(n)` without a stream).
Make contdc match the auction's private-stream pattern.

### B7. Stale `now` after a rejected bid defeats the vacancy gap
`auction_task.m:504–507`: after a bid is rejected, `boxVacantUntil(b)` is
computed from a `now` captured *before* the detail + bid screens (tens of
seconds earlier), so the vacancy window has usually already expired and the
box refills instantly — precisely the "infinite shuffle" behaviour the
`vacancyGapMean` comment in config.m says this mechanism exists to prevent.
Recompute `now = GetSecs - t0` before setting the timer (the same applies
after `showOutcome`'s 2.2 s feedback wait).

### B8. Market events are timestamped one frame early
`option_appear` / `option_remove` / `detail_enter` are logged against
`lastFlip` — the flip *before* the change is drawn. The change reaches the
screen on the *next* flip (~16.7 ms later at 60 Hz, more if the loop stalls).
The detail screen's own first flip is never logged at all. For gaze-locked
analysis, log against the flip that actually presents the change.

### B9. `cfg.et.sampleRateHz` is never applied
`setupEyeTracker` doesn't set the tracker's output frequency; the tracker
runs at whatever it was last configured to, while the saved config claims
60 Hz. Either set it via the SDK or record the actual
`et.obj.get_gaze_output_frequency()` into the data.

### B10. Two competing sources of truth for stimuli and paths
**Superseded 2026-09-25:** clean clones now use repo stimulus CSVs and
external runtime roots via `HW_DATA_ROOT`, `HW_PRACTICE_DATA_ROOT`,
`HW_ASSET_ROOT`, and `HW_TOBII_ROOT`.

`config.m` hardcodes the OSU share as `projRoot` and reads
`house_stimuli.csv` from the share — while the repo carries its own copy
that `STIMULI.md` calls "authoritative", and `STIMULI.md` describes a
`$DATA_ROOT` environment-variable scheme that no code implements. If the
share copy and repo copy drift, nothing will notice. Pick one story
(recommend: repo CSVs authoritative, synced to the share by a documented
step; fix STIMULI.md to match reality either way).

## C. Participant clarity

### C1. Right-click-to-reject is never explained — and it's an analysis aim
Rejection thresholds are analysis aim #3 (`README`), and the reject action
(right-click on a grid tile) is "the rejection-threshold data"
(`auction_task.m:436`). But **no instruction screen mentions it**. The
incentives instruction text says only "inspect any option that interests
you, and make an offer." A participant who is never told they can reject
will produce zero rejection data. This single gap can hollow out one of the
study's three research questions.

### C2. No practice trials or comprehension checks anywhere
The auction is a genuinely novel interface — options arriving/expiring,
left/right-click semantics, a semicircular bid arc. Participants get one
text screen and are then in trial 1 of 12, which is also real data. Add one
practice search episode (flagged `practice` in the data) and, ideally, two
or three comprehension questions after the instructions.

### C3. The bid screen has no visible way out, and its cancel button is wrong
`getBid` accepts on `buttons(1)` and cancels on `buttons(2)` — the *middle*
button. Right-click (`buttons(3)`) does nothing, no on-screen text explains
any way back, yet the detail screen just taught "RIGHT CLICK to go back".
Make right-click cancel and say so on screen.

### C4. Silent endings
- Episode ends by timeout/exhaustion → screen jumps to the next fixation
  with no acknowledgment. A one-line "The market has closed" screen would
  stop participants wondering whether they broke something.
- Choice trials: no visual confirmation of which card was clicked, and the
  15 s timeout ends the trial silently.

### C5. `q` aborts instantly, unconfirmed, from any keyboard state
`utils.checkForQuit` kills the session on a bare `q` keypress with no
modifier and no confirmation. A participant brushing the keyboard ends the
run (recorded as `crashed`; the `quit` status in `endRun` is never used).
Suggest requiring e.g. Ctrl+Q, or a confirm step, and recording status
`quit`.

### C6. Fonts will silently substitute on the lab machine
`Press Start 2P` must be installed (README open item, still open);
`Helvetica` is not a stock Windows font (PTB will substitute); the declared
`fontChromeAlt` fallback has no implementing code. Verify on the rig or add
a startup font check.

## D. Flexibility — "decide which parts a participant will see"

The PLAN mechanism already covers the important axes cleanly: task × domain
× session per row, `FORCE_DOMAIN` for quick tests, `JOBS_ARM` per session,
`forceCompetition`/`forceAttrLevel` in testing config, counterbalancing by
parity. This is in good shape. What's missing:

### D1. No dry-run / preflight
There's no way to see the fully-resolved design (blocks, trial counts,
estimated duration, attribute levels, window sizes) without launching PTB.
A `preflight.m` that takes a participant number and prints the resolved
PLAN, block schedule, and runs `verifyPaths` + `checkImages` + `checkAOIs`
for both layouts would (a) let you finalize the design decision on paper,
(b) become the RA's morning-of checklist.

### D2. The decision surface is scattered
"What does participant N see" is decided across `run_battery.m` (PLAN,
JOBS_ARM, COUNTERBAL), `config.m` (attrLevels, attrMethod, nTrials, nPairs,
sampling), and `incentives.m` (enabled). Add one table to
`experiment/README.md` listing every knob, its location, and its current
value, so the final design decision is one pass down one table.

### D3. Testing-mode rigidity
`cfg.testing.skipInstructions`/`skipElicitation` are hardcoded `true`, so
you cannot rehearse the instruction/elicitation flow in windowed mode
without editing config.m. Make them settable from `run_battery.m`.
